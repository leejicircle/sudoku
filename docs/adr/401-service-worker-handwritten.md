# ADR-401: 서비스워커 직접 작성 (Serwist / next-pwa 미도입)

## Status

Accepted

## Context

PWA 설치와 오프라인 플레이를 위해 서비스워커가 필요했다.
Next.js 진영의 표준 선택지는 Serwist(구 next-pwa)이지만, 이 앱이 실제로 필요한 것은

- 해시된 정적 자산 캐싱
- 오프라인 시 페이지 셸 폴백
- API·인증 응답은 캐시하지 않기

세 가지뿐이었다. 이를 위해 빌드 통합 · 프리캐시 매니페스트 생성 · 플러그인 설정이
따라오는 의존성을 추가하는 것은 규모에 비해 과했다.

## Decision

**라이브러리 없이 `public/sw.js`를 직접 작성한다** (약 70줄).
`registerServiceWorker()`는 `providers.tsx`에서 **프로덕션에서만** 호출한다
(개발 중 캐싱 혼란 방지).

### 캐싱 전략

| 대상 | 전략 |
|------|------|
| `_next/static`, `/icons/`, 폰트 등 해시·불변 자산 | cache-first |
| 페이지 네비게이션 (`request.mode === "navigate"`) | network-first → 실패 시 캐시, 최종 폴백 `/` |
| `/api/*` (인증 포함) | **캐시 금지 — 항상 네트워크** |
| 외부 오리진, GET 이외 메서드 | 개입하지 않음 (패스스루) |

`install`에서 오프라인 폴백용으로 `/`만 미리 캐시한다. 그 외 프리캐시는 없다.

## Consequences

**긍정적**

- 의존성 0. 캐싱 동작 전체가 한 파일에 있어 읽고 고치기 쉽다
- 빌드 파이프라인에 손대지 않아 Next.js 버전 업그레이드와 충돌하지 않음
- `/api/*` 제외가 명시적이라 인증·랭킹 응답이 캐시될 여지가 없음

**부정적 / 알려진 한계**

- **캐시 이름이 `sudoku-v1`로 고정.** `activate`에서 이름이 다른 캐시만 지우므로
  배포를 거듭해도 같은 캐시에 구버전 청크가 계속 누적된다(스토리지 증가).
  당장은 무해하지만, 정리하려면 배포마다 캐시 이름을 바꾸는 수단이 필요하다.
- **응답 상태코드를 확인하지 않고 캐시한다.** 정적·네비게이션 양쪽 모두
  `res.ok` 가드가 없어 404/500 응답도 캐시에 들어가고, 이후 오프라인 폴백으로
  제공될 수 있다. 후속 과제.
- 프리캐시가 없어 **첫 방문 직후 오프라인 전환 시** 아직 가져오지 않은 라우트는 열리지 않는다.

### 업그레이드 경로

프리캐시 매니페스트(빌드 산출물 목록 자동 주입)나 버전별 캐시 무효화가 필요해지면
그때 Serwist를 도입한다. 현재 `sw.js`는 런타임 캐싱만 하므로 교체 비용이 작다.
